# Collector and Operator Sign-up Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let anyone submit a sign-up as a collector or operator, hold it as pending, and let staff approve or reject it from the dashboard.

**Architecture:** A new `signup_requests` table and a `SignupsModule` in the NestJS backend own the whole lifecycle (submit, list, approve, reject, expire). Approval creates the real `users` or `collectors` row in one transaction. The Next.js dashboard gets a public `/signup` page (split layout, server actions only) and a staff `/signups` page.

**Tech Stack:** NestJS 10, TypeORM (migrations only, `synchronize` off), class-validator, argon2, vitest (backend). Next.js 15 App Router with server actions, plain CSS in `(operator)/globals.css` (dashboard; no test runner, verified by `typecheck` and a Playwright script in `e2e/`).

**Spec:** `docs/superpowers/specs/2026-11-15-signup-design.md`

## Global Constraints

- Schema changes only through a hand-written TypeORM migration in `apps/backend/src/database/migrations/`; never enable `synchronize`.
- Backend `ValidationPipe` has `forbidNonWhitelisted: true`: the dashboard sends only fields `CreateSignupDto` declares.
- Phone rule everywhere: `^\+?[0-9]{7,15}$`. Password: min `PASSWORD_MIN_LENGTH` (12), max 200. Name: non-empty after trim, max 200.
- Emails are trimmed and lower-cased before any comparison or storage.
- `passwordHash` never leaves the service: not in any return value, DTO, log or page.
- Pending requests expire after 14 days. Pending ceiling default 500, env `SIGNUP_MAX_PENDING`.
- Dashboard visuals use existing tokens in `apps/dashboard/src/app/(operator)/globals.css` (`--paper`, `--surface`, `--ink`, `--rule`, `--accent`, `--shadow-hard`, `--radius-*`, `--text-*`). No new colours or fonts. No all-caps or monospace labels (`docs/typography.md`).
- Exact copy from the spec (welcome panel, labels, confirmation, empty state, sign-in hint) is used verbatim.
- Work on a new branch `feat/signup` cut from `main`. The current branch `chore/mobile-expo-sdk-58` has unrelated uncommitted mobile changes that must not be touched or committed.

## Review Focus

1. **Email typed with capitals or spaces** (`" Ops@Example.com "`) when `ops@example.com` already exists: must conflict, not create a second request. Test in Task 2.
2. **Same person presses "Create account" twice**: the second submit gets a plain conflict message, never a second row and never a 500. Test in Task 2.
3. **Two staff approve the same request at once**: exactly one user/collector is created; the loser gets a conflict. Test in Task 3.
4. **Phone or email taken between sign-up and approval**: approval fails with a conflict and the request stays pending with its hash intact. Test in Task 3.
5. **Hub id that is well-formed but does not exist** (stale page, deleted hub): a conflict with a readable message, not a foreign-key 500. Test in Task 2.

**Files:**

- Test: `apps/backend/test/signups.service.test.ts` (setup modelled on `apps/backend/test/walkin-claims.test.ts`: `createTestDatabase`, `db.reset()`, `seedHub`)

**Interfaces:**
- Consumes: `SignupRequestEntity` (Task 1); `AuthService.hashPassword`.
- Produces:

```ts
export const SIGNUP_OPTIONS = "SIGNUP_OPTIONS";
export interface SignupOptions { maxPending?: number; now?: () => Date }   // defaults 500, () => new Date()
export const SIGNUP_EXPIRY_DAYS = 14;

export interface SubmitSignupInput {
  role: "collector" | "operator";
  name: string; phone: string;
  email?: string; password?: string;   // operator
  hubId?: string;                      // collector
}
export interface SignupReceipt { id: string; role: SignupRole; name: string; status: "pending" }

@Injectable()
export class SignupsService {
  constructor(
    @InjectDataSource() dataSource: DataSource,
    @Optional() @Inject(SIGNUP_OPTIONS) options?: SignupOptions,
  );
  submit(input: SubmitSignupInput): Promise<SignupReceipt>;
  /** Marks pending rows older than 14 days as expired and clears their hash. */
  private expireStale(manager: EntityManager): Promise<void>;
}
```

Rules `submit` enforces, in order, inside one transaction: `expireStale`; trim name and phone, trim+lower-case email; pending count `>= maxPending` → `ServiceUnavailableException("Sign-ups are paused for the moment. Please try again later.")`; operator: email exists in `users` → `ConflictException("An account with this email already exists.")`, pending request with that email → `ConflictException("A sign-up with this email is already waiting for approval.")`; collector: hub missing → `ConflictException("That hub is no longer available. Choose another hub.")`, phone exists in `collectors` → `ConflictException("A collector with this phone number already exists.")`, pending collector request with that phone → `ConflictException("A sign-up with this phone number is already waiting for approval.")`. Operator requests store `email` + `passwordHash`, `hubId` null; collector requests store `hubId`, `email` and `passwordHash` null (ignore any email/password sent). A unique-index violation on save maps to the matching "already waiting" conflict.

### Task 3: Listing, approving and rejecting

**Files:**
- Modify: `apps/backend/src/signups/signups.service.ts`
- Test: `apps/backend/test/signups.decisions.test.ts`

**Interfaces:**
- Consumes: Task 2's service; `JwtPayload`/`Role` from `apps/backend/src/auth/auth.module.ts`; `UserEntity`, `CollectorEntity`, `HubEntity`.
- Produces:

```ts
export interface SignupView {
  id: string; role: SignupRole; name: string; phone: string;
  email: string | null; hubId: string | null; hubName: string | null;
  status: SignupStatus; createdAt: string;            // ISO
}
export interface SignupDecision {
  signup: SignupView;
  createdUserId: string | null; createdCollectorId: string | null;
}
type Actor = { sub: string; role: Role };

listPending(actor: Actor): Promise<SignupView[]>;      // oldest first
approve(id: string, actor: Actor): Promise<SignupDecision>;
reject(id: string, actor: Actor): Promise<SignupDecision>;
```

Rules: every method runs `expireStale` first. Permission: `admin` → all requests; `operator` → collector requests only (list filters them; approve/reject of an operator request → `ForbiddenException("Only an admin can decide operator sign-ups.")`); any other role → `ForbiddenException`. `approve`/`reject` load the row with `pessimistic_write` lock in a transaction; missing → `NotFoundException`; status not `pending` → `ConflictException("This sign-up has already been <status>.")`. Approve operator: email now in `users` → `ConflictException("An account with this email now exists. Reject this sign-up or ask the applicant to use another email.")` and the transaction rolls back; else insert `users` row `{ email, passwordHash, role: "operator", active: true }`, set `createdUserId`, then set the request's `passwordHash` to null. Approve collector: phone now in `collectors` → `ConflictException("A collector with this phone number now exists. Reject this sign-up.")`; else insert `collectors` row `{ name, phone, kycLevel: "none" }`, set `createdCollectorId`. Both set `status`, `decidedAt = now()`, `decidedByUserId = actor.sub`. Reject sets status `rejected`, the decided fields, and `passwordHash` null.
